# X3DH и Double Ratchet: сетевой протокол v3

[English](X3DH.md) | **Русский**

Carriex устанавливает сеансы через X3DH и обменивается сообщениями через классический Double Ratchet. Оба телефона должны обновиться вместе. Существующий API предварительных ключей v2 совместим; сервер передаёт непрозрачные конверты v3 без секретов ratchet. Сохранённая история читается, а ожидающие исходящие сообщения с фиксированным ключом получают новые ID и шифруются заново. Неподписанные старые обмены ключами и сообщения прежних форматов отклоняются; автоматического понижения защиты нет. Получатель без подключения должен предварительно хотя бы раз опубликовать ключи.

## Криптография и идентичность

X25519, подписанные предварительные ключи XEd25519 и HKDF-SHA256 следуют [X3DH](https://signal.org/docs/specifications/x3dh/). Кодировка открытого ключа — `05` и 32 байта X25519. HKDF использует 32 байта `FF` перед DH1..DH3 и DH4 при одноразовом ключе, нулевую 32-байтовую соль и info `Carriex X3DH v2`. Нативный адаптер следует [XEdDSA](https://signal.org/docs/specifications/xeddsa/), используя операции libsodium со скалярами, точками, SHA-512 и проверкой Ed25519. Проверка отклоняет неканонические кодировки Montgomery и использует строгую проверку Ed25519 libsodium. Дополнительная криптографическая зависимость не загружается.

Ключ аутентификации P-256 подписывает следующие ASCII-байты без завершающего перевода строки:

```text
Carriex encryption identity v2
<64 lowercase hex device ID>
<canonical base64 X25519 identity public key>
```

Клиент сверяет SHA-256 канонического P-256 SPKI с ID контакта, проверяет привязку и подписанный предварительный ключ, закрепляет ключ шифрования отдельно для сервера. Сканирование QR-кода ID по доверенному каналу аутентифицирует эту привязку. Имена контактов — локальные подписи, а не идентичности. Смена закреплённого ключа отклоняется. Потеря ключа требует новой идентичности устройства; автоматического сброса ключа с прежним ID нет.

Закрытый P-256 неизвлекаем и остаётся в Android Keystore. Ключ идентичности X25519, предварительные ключи и секреты сеансов шифруются в SQLite телефона AES-GCM ключом Keystore и временно появляются в памяти для использования. Удаление выполняется в пределах возможностей платформы: управляемая память, страницы/WAL SQLite, flash и снимки файловой системы не позволяют обещать физически безопасное стирание. Резервное копирование/перенос приложения отключены.

## Передача Double Ratchet

Автомат состояний следует [разделу 3 Double Ratchet](https://signal.org/docs/specifications/doubleratchet/). Формат и криптографическая реализация принадлежат Carriex и не совместимы с сетевым форматом Signal. Шифрования заголовков и постквантовых ratchet нет.

32-байтовый результат X3DH инициализирует корневой ключ. Алиса создаёт независимую ratchet-пару X25519 и инициализирует её против подписанного предварительного ключа Боба. Боб сначала использует эту пару предварительного ключа, выводит получающую цепочку при первом аутентифицированном получении, затем создаёт новую пару и отправляющую цепочку до ответа. Каждый следующий новый открытый ratchet-ключ собеседника обновляет корень получения/отправки и создаёт новую локальную пару. Исходный общий секрет X3DH и эфемерный закрытый ключ не сохраняются. Состояние хранит текущий корень и DH-пару, текущие цепочки, счётчики и ограниченные пропущенные ключи.

`KDF_RK` — HKDF-SHA256 со старым корнем как солью, сырым результатом X25519 DH как входом, info `Carriex Double Ratchet v1 root` и выходом 64 байта: корень, затем цепочка. `KDF_CK` использует HMAC-SHA256(chain, `02`) для следующей цепочки и HMAC-SHA256(chain, `01`) для одноразового ключа сообщения. Старые значения цепочек, корня и DH заменяются; ключ сообщения стирается после использования в пределах возможностей среды/хранилища. Шифрование — XChaCha20-Poly1305 с новым случайным 24-байтовым nonce перед шифротекстом. DH-ключи заголовка — канонические сырые 32 байта X25519 в base64.

Начальные аутентифицируемые байты: ASCII `Carriex session v3\n`, две кодировки `05 || X25519 identity`, затем следующие ASCII-поля по порядку, каждое с четырёхбайтовой big-endian длиной в байтах:

```text
sender, recipient, identity_key, auth_key, binding, recipient_identity,
ephemeral, signed_id, one_time_id, created_at, protocol, ratchet_key
```

`created_at` — Unix-миллисекунды десятичным текстом; `protocol` точно равен `Carriex Double Ratchet v1`; `ratchet_key` — начальный открытый ratchet-ключ Алисы. ID сеанса — SHA-256 этих байтов. Для явного резервного режима `one_time_id` пуст. Первые поступившие сообщения должны указывать исходный ratchet-ключ, даже если их номер не нулевой.

Конверт DATA содержит `version:3`, `sid`, `mode` (`init` для инициатора X3DH, `reply` для отвечающего), `ratchet:{dh,pn,n}` и base64 `ciphertext`. Конверты инициатора всегда повторяют исходный `header`, включая последующие DH-переходы, чтобы начальные сообщения расшифровывались не по порядку. Режим обозначает роль в сеансе, а не текущий ход ratchet. `pn` — длина предыдущей отправляющей цепочки; `n` — номер текущего сообщения от нуля. Оба — целые JSON, не строки и не дробные, в неотрицательном signed-32 диапазоне, `n` максимум 2^31-2.

Связанные данные: ASCII `Carriex message v3\n<sid>\n<mode>\n<sender>\n<recipient>\n<message ID>\n`, затем канонические байты установления и `05 || dh || uint32_be(pn) || uint32_be(n)`. Поэтому идентичности, маршруты, ID сообщения, установление, открытый ratchet-ключ и счётчики аутентифицированы. Тело включает исходное время отправителя.

Пропущенные ключи индексируются по удалённому DH-ключу и номеру. На сеанс допускается до 1000 пропущенных/хранимых ключей, на контакт по всем сеансам — 2048. Разрыв свыше 1000 отклоняется до неограниченных вычислений. Пропущенный ключ истекает через наибольший объявленный TTL очереди от вывода, очищается при обработке/обслуживании и расходуется только после успешной аутентификации. Поздние сообщения за пределами лимитов не расшифровываются. Повторы отклоняются; обычная повторная доставка подтверждается по постоянной истории ID. Неудачная аутентификация не фиксирует счётчики, DH-переходы и удаление ключей.

Состояние ratchet и точный исходящий шифротекст фиксируются вместе до сети. Повторы передают сохранённые байты в пределах срока хранения получающих ключей, в том числе после 30-дневного предела новых сообщений, не продвигая ratchet. Открытый текст ограничен 90 КиБ UTF-8; окончательный транспортный размер проверяется до фиксации отправки. Постоянный отказ помечается **Ошибка**, а не повторяется бесконечно. При невосстановимом разрыве **меню чата → Начать новый защищённый сеанс** прекращает новые отправки старого сеанса; следующее сообщение начинает X3DH. Получающие ключи, история и существующий шифротекст сохраняются. Входящее состояние, расход предварительного ключа и история фиксируются вместе до подтверждения. Состояние и пропущенные ключи переживают перезапуск в SQLite под защитой Keystore.

На область сервера допускается 4096 сеансов, на контакт — 16 сохранённых и четыре новых в сутки по часам допуска получателя. Неизвестные отправители попадают в запросы без создания сеанса; поддерживается до 128 контактов. Одновременное начало сохраняет оба сеанса и выбирает новейший пригодный, разрешая равенство по ID. Новые сообщения отправляются 30 дней, после чего требуется X3DH. Текущее ratchet-состояние хранится до момента создания сеанса плюс 37 дней и наибольший TTL очереди. История остаётся читаемой. Истёкшая ожидающая отправка показывает **Срок истёк**; скопируйте текст и отправьте снова. Очистка идёт при работе приложения, не когда оно выключено.

**Ограничения:** развитие ключей предназначено для защиты израсходованных ключей после удаления и восстановления после пассивной компрометации состояния при новых незатронутых DH-вкладах. Текущая цепочка раскрывает будущие сообщения этой цепочки до нового DH; сохранённые пропущенные ключи раскрывают соответствующие сообщения. Контроль устройства, кража идентичности, активные атаки, плохая случайность и восстанавливаемое старое состояние могут нарушить защиту. Гарантии против отката SQLite и криминалистического восстановления удалённых данных нет. История открытых сообщений доступна скомпрометированному разблокированному приложению. Протокол классический, не постквантовый, без независимого аудита. Сервер видит маршруты, время, длины и открытые ratchet-заголовки; может скрывать ключи/сообщения и лгать о доставке.

## Адреса API сервера

Все адреса требуют bearer-аутентификации и HTTPS вне локальной разработки. Ответы используют `Cache-Control: no-store`.

| Адрес | Назначение |
|---|---|
| `POST /prekeys` | Публикация собственного набора и до 100 одноразовых предварительных ключей |
| `GET /prekeys/status` | Собственное количество доступных ключей, ревизия, последнее подтверждение и `message_ttl_seconds` |
| `POST /prekeys/<peer ID>/claim` | Атомарная выдача набора с расходованием не более одного ключа |

Публикация содержит `version:2`, монотонную целую `revision`, случайный 32-hex `publication_id`, `identity_key`, `auth_key`, `binding`, `signed_prekey:{id,key,signature}`, `one_time_prekeys:[{id,key}]`. Ответ выдачи содержит `user_id`, поля сертификата/подписанного ключа и `one_time_prekey:{id,key}` либо `null`. Ключи/подписи — канонический base64, ID предварительного ключа — 32 строчных hex. Первые восемь hex нового ID одноразового ключа кодируют ревизию публикации. Клиенты проверяют XEdDSA; сервер проверяет привязку сертификата и размеры открытых полей. Закрытых ключей он не хранит.

Выдача SQLite атомарна, в том числе при конкурентных запросах. Израсходованные и истёкшие открытые ключи физически удаляются из каталога. На владельца сервер сохраняет только SHA-256 манифеста последней публикации и её подтверждение, без второй копии израсходованных ключей. Точный повтор той же ревизии возвращает прежнее подтверждение без вставки ключей. Изменённая та же ревизия и старые загрузки отклоняются; следующая ревизия должна увеличиться на один. Новая запись каталога принимает существующий положительный счётчик телефона. Префикс ревизии в ID не позволяет вернуть старый израсходованный ключ в новой публикации. Сохраняйте базу сервера: потеря ревизий уничтожает историю защиты от повторов, восстановление старого снимка не защищено от отката.

Отсутствующий контакт даёт 404, некорректный набор — 400, конфликт ID/ключа — 409, вместимость/частота — 429. Лимиты доступных ключей: 200 на владельца, 20 000 всего, 4096 владельцев; два последних настраиваются `PREKEY_GLOBAL_LIMIT`, `PREKEY_OWNER_LIMIT`. Выдачи ограничены 30 на аутентифицированного отправителя и 100 на получателя в минуту; счётчики переживают перезапуск. Они ограничивают случайные/избыточные запросы, но не предотвращают отказ в обслуживании множеством подставных устройств.

Телефон сначала создаёт 50 одноразовых ключей и пополняет при остатке менее 10: до 2048 закрытых OPK, до 50 новых за шесть часов и 200 в сутки. Бюджет сохраняется после переподключения/перезапуска. При исчерпании генерация приостанавливается с предупреждением; существующие сеансы работают. Старые закрытые ключи хранятся до безопасного срока, а не удаляются ради места. Обслуживание инвентаря идёт при публикации, не при каждом сообщении; запускается при подключении и ежечасно при опросе.

Точная ожидающая публикация сохраняется до загрузки. Только совпавшее успешное подтверждение активирует новый подписанный ключ, выводит прежний из активных и начинает срок хранения закрытых ключей. Потерянный ответ восстанавливается через подтверждение статуса. Подписанные предварительные ключи обновляются через семь дней подтверждённой активности; выведенные закрытые остаются на TTL плюс 37 дней. Одноразовые открытые истекают через семь дней после загрузки. Неиспользованные закрытые сохраняются на TTL плюс 44 дня после подтверждённой публикации, покрывая выдачу, 30 дней отправки сеанса и задержку очереди. Израсходованный закрытый удаляется в транзакции первого принятого сообщения. Неподтверждённые ключи защищены от преждевременной очистки. Клиенты поддерживают TTL до 365 дней, помнят максимум и продлевают существующие сроки при его росте. Это логические ограничения/удаления строк, а не гарантия сжатия файла SQLite или физического стирания.

Сеансы без одноразового ключа по умолчанию запрещены и при начале, и при принятии. Пользователь может явно включить резервный режим в **Безопасность чатов**. **ID контакта** показывает защиту последнего установленного/полученного сеанса. Иначе исчерпание ключей вызывает понятную ошибку и требует пополнения.

## Изоляция входящих и ограничения хранилища

`GET /messages/<owner>?after=<cursor>` выдаёт очередь по непрозрачному целочисленному курсору, по 500 записей. Клиент разбирает записи независимо и продолжает следующие страницы. Неверный шифротекст помещается в зашифрованный локальный карантин и снимается с сервера через `POST /messages/<owner>/ack`, `quarantine:true`, без отчёта доставки. Явное принятие после успешной расшифровки может позднее отправить обычное подтверждение.

Неизвестные отправители отображаются в **Запросы на переписку**. Принятие добавляет контакт и пытается расшифровать; неверный запрос можно удалить или заблокировать. Карантин: до 64 записей, до двух на отправителя, приблизительно 4 МиБ на сервер, срок локального хранения 30 дней. При заполнении дополнительные запросы удаляются с ошибкой. Клиент публикует до 128 контактов и 128 блокировок через `POST /messages/<owner>/policy`; сервер видит списки. Блокировка снимает очередь без подтверждения и отклоняет последующие отправки.

Сервер ограничивает неизвестных отправителей двумя записями каждого и 32 суммарно, известных — 64 на каждого, получателя — 1000 всего. Шифротекст: 256 КиБ на сообщение, 16 МиБ на получателя, 128 МиБ глобально; все строки, включая статусы доставки, — до 50 000. Политики входящих — до 4096 владельцев. Очистка TTL удаляет истёкшие служебные записи подтверждений/карантина. Лимиты сдерживают рост, но не гарантируют доступность против множества зарегистрированных атакующих.

## Сбои и миграция

Телефон фиксирует состояние сеанса и точный исходящий конверт вместе до отправки. Входящая аутентификация, сохранение сеанса, удаление одноразового ключа и вставка истории фиксируются вместе до уведомления UI и подтверждения. Ошибка аутентификации откатывает всё. ID уникальны в области сервера. Обновление базы сохраняет текст и время, удаляет устаревшие ожидающие обмены, повторно шифрует только исходящие со статусом отправки. Старые фиксированные ключи больше не загружаются подсистемой сообщений. Сервер должен поддерживать подтверждения/ревизии публикаций и политики входящих из API v2.

База версии 7 удаляет корни фиксированных сеансов, сохраняя идентичность, предварительные ключи, закрепления и историю. Конверты v2 отклоняются без понижения версии. Оба телефона должны обновиться; API предварительных ключей не требует специального изменения для ratchet. Новая установка не восстанавливает старые закрытые ключи.

Старые ожидающие сообщения с уже сохранённым пакетом получают новый ID и шифруются локально при миграции, чтобы не конфликтовать с прежним шифротекстом, который сервер мог принять при потерянном HTTP-ответе. Если старый вариант уже получен, неопределённая доставка может создать дубликат. По возможности завершите ожидающую доставку на старых клиентах до обновления. Уже поставленный в очередь старый шифротекст сервер не преобразует.

## Проверка

Серверные тесты используют настоящий localhost HTTP: привязка владельца, неверные публикации, конкурентные выдачи, ограничения частоты, конфликты и сохранение после перезапуска. Android `X3dhAndroidTest` использует JNI и зашифрованную SQLite, независимые векторы Python XEdDSA и трёх/четырёх DH, подмену, откат, перезапуск, одновременное начало и доставку не по порядку. Векторы воспроизводятся через `Carriex/tools/x3dh_reference_vectors.py` и `Carriex/tools/double_ratchet_reference_vectors.py` в Python-окружении сервера.

`DoubleRatchetTest` проверяет независимые Python KDF/DH-векторы, порядок между цепочками, откат при повторах/подмене, границы счётчиков, сроки ключей и пределы компрометации. `DoubleRatchetAndroidTest` повторяет их с JNI и сохраняемыми SQLite/outbox/пропущенными ключами; тесты хранилища покрывают v6 → v7.

Для полного Android–Flask запустите изолированный локальный сервер на 18765 с `CARRIEX_ALLOW_INSECURE_HTTP=1` и временным `CARRIEX_DATA_DIR`. Из `Carriex` на эмуляторе:

```powershell
.\gradlew.bat :app:connectedDebugAndroidTest '-Pandroid.testInstrumentationRunnerArguments.class=com.example.carriex.crypto.x3dh.X3dhServerAndroidTest' '-Pandroid.testInstrumentationRunnerArguments.x3dhServer=http://10.0.2.2:18765'
```

Живой тест проверяет первое сообщение отключённому получателю, непрозрачный шифротекст очереди, шифрование ответа, перезапуск получателя и дальнейшие DH-переходы без новой выдачи предварительного ключа. Без аргумента сервера этот один тест явно пропускается.
