# Сервер Carriex

[English](DEVELOPMENT.md) | **Русский**

Сервер Flask и Flask-Sock пересылает непрозрачные зашифрованные данные через HTTP и WebSocket. Сам он их не шифрует и не расшифровывает.

## Подключение телефонов (рекомендуется)

В Windows запустите `start-server.bat`, укажите доступный HTTPS IP-адрес и откройте созданный `.carriex-server/pairing.html`. Телефоны сканируют QR-код или импортируют текст, сохраняют сервер и подключаются с закреплённым ключом. Зарегистрированный домен, публичный CA и дополнительные приложения не нужны. Установка, домашняя сеть, резервирование ключей и Docker с прямым TLS описаны в [PAIRING.ru.md](PAIRING.ru.md).

## Локальная разработка API

Нужен Python 3.11 или новее. Аутентификация устройства обязательна. См. [протокол, TLS и переход со старых ID](AUTHENTICATION.ru.md). [X3DH и зашифрованные конверты](X3DH.ru.md) описывает защищённый API `/prekeys`, привязку ключей клиентов, обновление и повторы.

```sh
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell instead:
# .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
# Local development only; PowerShell: $env:CARRIEX_ALLOW_INSECURE_HTTP='1'
export CARRIEX_ALLOW_INSECURE_HTTP=1
python -m flask --app src.app:app run --host 127.0.0.1 --port 5000
```

`python main.py` запускает сервер с прямым HTTPS без отладки. Явная HTTP-команда выше остаётся для локальных тестов протокола.

## Архивная настройка TLS

Старая схема с частным CA сохранена в [deprecated/local-tls](../deprecated/local-tls/README.ru.md). Текущее приложение доверяет отдельным самоподписанным ключам через QR-код/текст, сохраняя проверку сертификатов HTTPS/WSS и имён узлов.

## Docker за обратным прокси (альтернативный API)

Для Android используйте `compose.paired.yaml` из [PAIRING.ru.md](PAIRING.ru.md). Прежний вариант ниже предназначен для клиентов с публичным CA на прокси; такой сертификат нельзя импортировать в приложение как самоподписанный сертификат отдельного сервера.

```sh
docker compose -f compose.proxy.yaml up --build -d
docker compose -f compose.proxy.yaml logs -f server
docker compose -f compose.proxy.yaml down
```

Compose по умолчанию публикует 5000 на loopback, но прежние `.env` HOST/PORT имеют приоритет. Держите backend закрытым и завершайте HTTPS на доверенном прокси. `CARRIEX_TRUST_PROXY=1` задавайте только если прокси перезаписывает заголовок схемы. `CARRIEX_AUTH_ORIGIN` должен точно совпадать с публичным HTTPS URL клиентов. Для локальной разработки явно включайте `CARRIEX_ALLOW_INSECURE_HTTP=1`. Ни одна настройка не отключает аутентификацию. Образ работает без root и проверяет общедоступный `/health`.

Без Compose:

```sh
docker build -t carriex-server .
docker run --rm -p 127.0.0.1:5000:5000 carriex-server
```

Контейнер использует один Gunicorn worker и 100 потоков. Активные WebSocket занимают потоки; оставляйте запас для HTTP. Не увеличивайте workers и число экземпляров: живые подключения и сеансы аутентификации локальны для процесса. Очереди шифротекста, открытые предварительные ключи и ограниченные учётные данные уведомлений сохраняются в SQLite. При перезапуске сохраняйте закрытый каталог данных.

## API

| Адрес | Поведение |
| --- | --- |
| `GET /health` | Состояние, версия проекта, подключённые пользователи и клиенты |
| `POST /auth/challenge` | Начинает доказательство владения открытым ключом P-256 |
| `POST /auth/verify` | Проверяет одноразовую подпись, регистрирует устройство и выдаёт сеанс |
| `POST /send` | Принимает `id` (32 строчных hex), `sender`, `recipient`, `ciphertext`; сохраняет в очереди и предлагает живую доставку |
| `GET /messages/<user_id>?after=<cursor>` | До 500 ожидающих сообщений с курсорами пагинации |
| `GET /messages/<user_id>/count` | Только `pending_count` и ревизия поступления `revision`, без загрузки/подтверждения |
| `POST /notifications/token` | Выдаёт/заменяет постоянные данные только для GET собственного количества |
| `DELETE /notifications/token` | Отзывает их; требуется полная аутентификация |
| `POST /messages/<user_id>/ack` | Принимает `ids`, необязательные `report_delivery` или `quarantine`; карантин подавляет отчёты |
| `POST /messages/<user_id>/policy` | Ограниченные списки контактов/блокировок и резервирование входящих |
| `GET /statuses/<user_id>` | Видимые отправителю состояния `queued` / `received` |
| `WS /ws/<user_id>` | Ожидающие и живые сообщения; поддерживает `ack` и события подтверждений |

Адреса сообщений и открытие WebSocket требуют `Authorization: Bearer <token>`. Получение токена описано в [AUTHENTICATION.ru.md](AUTHENTICATION.ru.md). [Протокол уведомлений](NOTIFICATIONS.ru.md) объясняет ограниченные учётные данные, планирование Android, интервалы и измерения. ID в примерах — обозначения полных 64-символьных отпечатков открытых ключей.

WebSocket-клиент отправляет `{"type":"health"}` или `{"type":"send","recipient":"bob","ciphertext":"encrypted-payload"}`. Отправитель берётся из ID соединения. Ответы: `health`, `sent`, `error`; доставка имеет вид `{"type":"message","message":{"id":"...","from":"alice","ciphertext":"encrypted-payload","timestamp":"..."}}`.

ID аутентифицированы, входящие доступны только владельцу. Получение не удаляет сообщения. Сервер хранит шифротекст до подтверждения или TTL; повтор идемпотентен по ID. Открытые ключи аутентификации и сеансы пока в памяти. Для удалённого применения нужны TLS и ограничения частоты. См. [SECURITY.ru.md](SECURITY.ru.md).

## Проверки и упаковка

```sh
python -m pytest -q
python -m ruff check .
python -m build
```

Подробности интеграционных тестов: [tests/README.ru.md](../tests/README.ru.md). Зависимости определены в `pyproject.toml`; `requirements.txt` устанавливает extra для разработки. Диапазоны зависимостей не являются lockfile: сборка может выбрать новые совместимые версии.

## Версии

`src/_version.py` — единый источник версии, начиная с `0.1.0`. Setuptools читает его для метаданных; Python предоставляет `src.__version__`, `/health` сообщает ту же версию. Используется Semantic Versioning (`MAJOR.MINOR.PATCH`). В серии `0.x` минорные выпуски могут менять API; исправления должны сохранять совместимость.

Для выпуска обновите файл версии и перенесите `Unreleased` в датированный раздел истории изменений. Выполните проверки, объедините изменения, затем создайте соответствующий Git-тег, например `v0.1.0`, и выпуск GitHub по changelog. CI проверяет совпадение тега с метаданными. Автоматической публикации нет.

См. [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md). Лицензия пока не выбрана; репозиторий в настоящее время не предоставляет open-source лицензию.

### Проверки восстановления WebSocket

Серверные ping выполняются каждые 25 секунд. Переподключившийся клиент получает очередь; при ошибке отправки накопленного восстанавливаются неотправленный элемент и хвост. В Windows запускайте `.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider`. Тесты запускают изолированные localhost-серверы, покрывают переподключение, доставку накопленного и перекрывающиеся соединения одного пользователя. Очереди сохраняются после перезапуска; успешная запись в сокет не доказывает получение адресатом.
