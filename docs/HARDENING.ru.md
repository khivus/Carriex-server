# Публикация в интернете и восстановление

[English](HARDENING.md) | **Русский**

Обычный запуск Windows, Linux/macOS и Docker использует один ограниченный
производственный сервер gevent. Адрес, закрытый ключ TLS, закрепление сертификата
и audience аутентификации сохраняются. Остановите старый процесс, установите новые
зависимости и запустите прежний скрипт. Сохраните каталог/том идентичности; новые
ключи для обновления не нужны. Миграции SQLite выполняются автоматически.
При обновлении сохраняется регистрация ранее аутентифицированных владельцев
сообщений, предварительных ключей, политик входящих, токенов уведомлений и
подписанного участия в группах. Произвольный ID адресата и непринятое приглашение
не регистрируют устройство.

Обновите Android и на принимающих телефонах: подтверждения теперь сохраняются для
повтора после перезапуска, принятые/автоматически добавленные контакты обновляют
политику сервера, а временные ограничения отправки учитывают задержку повтора.
История и сеансы шифрования сохраняются.

## Почему отправка могла остановиться

Раньше сервер разрешал только 64 ожидающих пакета от принятого контакта и два от
неизвестного отправителя. Отключённый друг мог исчерпать первый лимит. Потерянное
подтверждение или устаревшая политика контактов могли оставить второй лимит даже
после принятия разговора. Лимит 64 удалён. Неизвестные запросы по-прежнему ограничены
двумя пакетами до принятия/получения адресатом, чтобы защитить входящие от спама.

У адресата остаётся максимум 1000 ожидающих сообщений / 16 МиБ. Общая очередь личных
сообщений: 50 000 записей / 128 МиБ. На отправителя приходится до 4000 ожидающих
сообщений / 8 МиБ и 10 000 сохранённых записей. После подтверждения шифротекст
освобождает байтовую квоту; небольшие записи доставки/идемпотентности остаются до TTL.
Эти значения рассчитаны на небольшой сервер. Масштабируйте измеряемые параметры,
не удаляя ожидающие сообщения и не отключая защиту от неизвестных контактов.

## Настройки доступа

Пробрасывайте только нужный TCP-порт HTTPS. Не публикуйте каталог данных, просмотр
статистики, HTTP backend, Docker API, SSH/RDP и управление маршрутизатором. Проверьте
правила IPv4 и IPv6. Ограничения до TLS/аутентификации и после неё:

| Контроль | По умолчанию |
|---|---|
| Все соединения / соединения с одного IP | 128 / 32 |
| Полное рукопожатие TLS | 5 секунд |
| Полные заголовки HTTP / полное тело запроса | По 15 секунд |
| Запись WebSocket / ожидание блокировки записи | По 5 секунд |
| WebSocket всего / на IP / на устройство | 64 / 20 / 2 |
| Буфер готовых сообщений WebSocket | 16 сообщений и 2 МиБ на сокет |
| Сообщения / байты WebSocket | 180 сообщений и 8 МиБ в минуту на сокет |
| HTTP на IP / всего | 600 / 6000 в минуту, ограниченные token bucket |
| Запросы аутентификации на IP / всего | 60 / 600 в минуту |
| Challenge на устройство/источник / сеансы устройства | 3 / 4; старые сеансы вытесняются |
| Новые устройства на источник / всего | 30 / 120 в час, сохраняется после рестарта |
| Ожидающие приглашения адресату | 16, отдельно от 64 принятых групп |

Лимиты учитывают всплески. Общий NAT делит ограничение IP между пользователями;
настройте его под реальную нагрузку. Основные параметры есть в `.env.example`.
Все записи `DEFAULTS` в `src/security.py` доступны с префиксом `CARRIEX_` в обычном
конфиге; дополнительные параметры Docker нужно явно передавать в environment.
Оставляйте общий лимит WebSocket ниже лимита всех соединений.

Общедоступный `GET /health` оставляет состояние, версию и совместимость для Android.
Количество активных пользователей/сокетов перенесено в защищённый `GET /diagnostics`.
Частные ответы имеют `Cache-Control: no-store`. Общедоступные запросы не создают
запись статистики на каждый вызов.

## Закрытая регистрация и локальное управление

Открытая регистрация остаётся доступной. Любой посетитель открытого сервера может
создать собственный ключ; аутентификация не является приглашением. Для сервера
друзей задайте `CARRIEX_REGISTRATION_MODE=approved` и подтвердите публичные ID
локально. QR устанавливает доверие к серверу, но не служит секретом регистрации.
Общедоступного интерфейса администратора и пароля администратора нет.

```powershell
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server list
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server approve DEVICE_ID
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server revoke DEVICE_ID
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server block DEVICE_ID
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server unblock DEVICE_ID
.\.venv\Scripts\python.exe -m src.admin --data-dir .carriex-server cleanup
```

В Linux/macOS используйте `.venv/bin/python`. В Docker:
`docker compose exec server python -m src.admin --data-dir /var/lib/carriex ACTION DEVICE_ID`.
Для `list`/`cleanup` ID не нужен. Оператору уже требуется доступ к закрытой базе.
`revoke` отзывает существующие полные сеансы и данные счётчика; устройство может
войти снова. `block` дополнительно запрещает новый вход. Разблокировка не возвращает
старые токены. Клиент может вызвать `DELETE /auth/session` для текущего сеанса или
`DELETE /auth/sessions` для всех своих сеансов и данных счётчика. Сокеты проверяют отзыв.

Неактивные неодобренные и незаблокированные записи каталога удаляются через 90 дней
с учётом TTL, неполученных очередей и текущего доступа к группам. Одобренные записи
и запреты сохраняются. История закрытых групп удаляется только после окна хранения;
активные подписанные цепочки сохраняются. Отказы/выходы/закрытые группы больше не
занимают слоты принятых групп, поэтому старое исчерпание автоматически устраняется
новым подсчётом без удаления истории. Блокировки действуют и на приглашения/запросы
предварительных ключей. Незнакомцы не расходуют последние девять одноразовых ключей,
зарезервированных для контактов/участников групп; пополнение по-прежнему срабатывает
ниже десяти. Лимиты пары и источника ограничивают многократные запросы.

## Прокси, хранилище и зависимости

Режим QR сам завершает TLS и игнорирует forwarded-заголовки. В расширенном режиме
прокси изолируйте backend и задайте `CARRIEX_PROXY_NETWORKS` с точными CIDR источников
прокси (по умолчанию только loopback). Прокси перезаписывает `X-Forwarded-Proto` и
`X-Forwarded-For`, сохраняет Authorization и поддерживает upgrade. Заголовки других
источников не превращают HTTP в HTTPS. Прокси на Docker-хосте может выглядеть как
адрес шлюза моста; разрешайте его проверенный адрес, а не недоверенную сеть целиком.
Оставляйте `CARRIEX_ALLOW_INSECURE_HTTP=0` на развёрнутом сервере.

Compose ограничивает память (512 МиБ), CPU, процессы, открытые файлы, временное место
и журналы. Предел базы SQLite по умолчанию — 1 ГиБ, также задан целевой размер WAL.
Это не дисковая квота для WAL, копий и прочих файлов: для жёсткого ограничения нужны
квота тома/файловой системы и контроль свободного места. Существующая база больше
предела не обрезается.

`requirements.lock` фиксирует проверенные версии производственных зависимостей;
Docker устанавливает их перед приложением. CI проверяет lock по актуальным
бюллетеням. Для обновления установите новые версии отдельно, проверьте сервер и
TLS/WSS, выполните `python tools/lock_dependencies.py`, затем
`python -m pip_audit -r requirements.lock --disable-pip --no-deps`.
Бюллетени и версии меняются: аудит относится к дате проверки, не даёт гарантии.

Программные лимиты не защищают уже забитый канал интернета. При необходимости
используйте защиту провайдера/маршрутизатора или ограниченный сетевой доступ.
Публичные порты, TLS и брандмауэр проверяются из другой сети; localhost-тесты не
доказывают правильность публичной конфигурации.
