# Обновление настроек и восстановление запуска

[English](CONFIGURATION.md) | **Русский**

При обновлении через pull сохраняйте существующий `.env`. Отсутствующие
необязательные параметры используют значения по умолчанию; заменять файл новым
примером не нужно. Сохраните также закрытый каталог идентичности или том Docker,
чтобы телефоны продолжали доверять прежнему ключу.

## Что изменилось в 0.7.0

Настройки адреса прежние: `CARRIEX_HOST`, `CARRIEX_PORT` и `CARRIEX_SERVER_NAME`.
Раздел 08 добавляет необязательные ограничения для сервера в интернете.
Закомментированные строки не действуют; пояснения содержат единицы и значения
по умолчанию.

| Параметр (добавьте префикс `CARRIEX_`) | По умолчанию | Назначение |
|---|---|---|
| `REGISTRATION_MODE` | `open` | `approved` требует локального одобрения ID каждого устройства; миграция сервера сохраняет уже зарегистрированные ID. |
| `CONNECTION_LIMIT` / `CONNECTIONS_PER_IP` | 128 / 32 | Ограничивают одновременные соединения, включая соединения до аутентификации. Пользователи за одним NAT делят лимит IP. |
| `REQUEST_TIMEOUT` | 15 секунд | Срок получения полных HTTP-заголовков и отдельно тела запроса. |
| `WS_GLOBAL_LIMIT` / `WS_IP_LIMIT` / `WS_DEVICE_LIMIT` | 64 / 20 / 2 | Ограничивают соединения WebSocket. |
| `ENROLL_IP_HOURLY` / `ENROLL_GLOBAL_HOURLY` | 30 / 120 | Ограничивают регистрацию новых устройств за час. |
| `SENDER_PENDING_LIMIT` / `SENDER_STORAGE_BYTES` | 4000 / 8 388 608 байт | Ограничивают очередь одного отправителя вместо прежнего лимита 64 сообщений для принятых контактов. |
| `MAX_DATABASE_BYTES` | 1 073 741 824 байта (1 ГиБ) | Максимальный размер SQLite без учёта WAL, журналов и резервных копий. |

Не раскомментируйте все параметры подряд. В частности, пример
`REGISTRATION_MODE=approved` включает ручной допуск; закомментированная строка
сохраняет обычную открытую регистрацию. TTL сообщений и необязательная статистика
имеют отдельные разделы. Раздел 09 отделяет прежний URL и настройки прокси от
обычного HTTPS с QR-подключением. Дополнительные ограничения, команды одобрения
и восстановления описаны в [HARDENING.ru.md](HARDENING.ru.md).

## Почему после pull сервер может не запуститься

Производственный слушатель 0.7.0 требует **gevent** и в Windows, и в Linux.
`git pull` обновляет исходники, но не устанавливает новые пакеты в существующее
виртуальное окружение. Поэтому старое окружение может завершиться с ошибкой
`ModuleNotFoundError: No module named 'gevent'`. После обновления только исходников
это вероятная причина; подтвердить её можно лишь по реальной ошибке запуска.

Однократное исправление для старой установки Windows из каталога сервера:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\start-server.bat --check-config
.\start-server.bat
```

Для Linux/macOS: `.venv/bin/python -m pip install -r requirements.txt`, затем
`sh start-server.sh --check-config` и `sh start-server.sh`.

Обновлённые обычные скрипты автоматически устанавливают зафиксированные зависимости
при изменении lock-файла или отсутствии нужного пакета. Для обновления нужен доступ
к интернету/индексу пакетов. Неудачная установка останавливает запуск с пояснением,
до создания файлов идентичности. При последующих запусках пакеты проверяются,
а pip не запускается. После применения lock-файла последующие ручные обновления
пакетов сохраняются до следующего изменения lock-файла. Прямой запуск
`python -m src.pairing` зависимости не устанавливает.

Для Docker после pull пересоберите и пересоздайте сервис:

```sh
docker compose up -d --build
docker compose logs --tail 100 server
```

Один перезапуск контейнера не пересобирает образ и не загружает изменённое
окружение Compose. Сохраняйте том идентичности: удалять его для исправления пакетов
не нужно. Если зависимости обновились, но запуск всё ещё не работает, найдите
в журнале конкретную ошибку настройки, занятый порт или отказ в доступе к данным,
вместо повторной замены `.env`.

## Автоматическая миграция настроек

Обычный запуск и `--pair-only` сравнивают сохранённый отпечаток шаблона с текущим
примером. При обновлении восстанавливаются заголовки разделов, пустые строки,
описания и закомментированные необязательные параметры. Активные значения сохраняют
буквальную запись, кавычки и комментарии в строке. Дополнительные переменные и
личные комментарии попадают в **PRESERVED ADVANCED SETTINGS AND PERSONAL NOTES**.
Прежний `CARRIEX_PUBLIC_URL` сохраняется без включения конфликтующего примера host.
Переопределения из оболочки/CLI не записываются в файл при автоматической миграции.

Перед заменой сервер сохраняет исходные байты рядом в
`.env.backup-YYYYMMDD-HHMMSS-<суффикс>`. Новый файл заменяет старый атомарно;
сохраняются UTF-8 BOM, переводы строк и режим доступа. Одновременное редактирование
обнаруживается. Резервные копии содержат настройки: храните их приватно.
Неизменившийся шаблон не вызывает повторной записи и лишней копии. Синтаксис и
рабочие лимиты проверяются до автоматической миграции и создания идентичности.

Флаги для любого обычного скрипта запуска:

| Флаг | Действие |
|---|---|
| `--check-config` | Проверка и просмотр без записи конфига/идентичности, слушателя и загрузки зависимостей. |
| `--migrate-config` | Только обновление оформления с копией. При отсутствии файла создаёт закомментированный шаблон без выдуманного адреса. Нет идентичности и слушателя. |
| `--no-migrate-config` | Запуск с существующими значениями без перезаписи файла настроек. |
| `--init-config` | Добавляет недостающие адрес/порт/имя из сохранённого адреса или `--address` в шаблон с категориями. |

Все флаги поддерживают `--config path/to/custom.env`. Если корректный файл доступен
только для чтения или копию создать нельзя, автоматическая миграция предупреждает
и продолжает с проверенными значениями. Явный `--migrate-config` сообщает об ошибке.
Миграция не заменяет закрытый ключ сервера, базу данных и историю сообщений.

Docker Compose читает `.env` хоста и передаёт выбранные значения в контейнер;
стандартный сервис этот файл **не монтирует**. Поэтому автоматически переписать
файл хоста он не может. Сохраните существующий `.env`: новые параметры используют
значения по умолчанию. Для обновления оформления собранным образом выполните из
каталога репозитория (каталог должен быть доступен пользователю контейнера на запись):

```sh
docker compose run --rm --no-deps --entrypoint python --volume "${PWD}:/settings" server -m src.pairing --config /settings/.env --migrate-config
```

Команда создаёт только конфиг/копию на хосте, без слушателя и изменения
идентичности. После редактирования активных значений пересоздайте сервис через
`docker compose up -d`. Дополнительные параметры Docker нужно также передавать
в Compose `environment`.
