# Аутентификация устройства (протокол v1)

[English](AUTHENTICATION.md) | **Русский**

Приложение создаёт пару ECDSA P-256 в Android Keystore. На Android 9+ запрашивается StrongBox; при его недоступности используется обычный Keystore. Закрытый ключ неизвлекаемый, степень аппаратной изоляции зависит от устройства. Подпись разрешена без биометрического запроса, чтобы переподключение работало автоматически. Ключи аутентификации отделены от ключей шифрования сообщений. Резервное копирование и перенос приложения отключены, чтобы не восстановить ID без его ключа Keystore. Переустановка или очистка данных уничтожает идентичность; восстановления, экспорта и смены ключа пока нет.

ID пользователя — 64 строчных шестнадцатеричных символа SHA-256 канонического открытого ключа DER SubjectPublicKeyInfo. Он заменяет прежние случайные `user-...`; существующим пользователям нужно сообщить новые ID. Другой ключ не может зарегистрировать существующий ID, в том числе после перезапуска сервера. Клиент не выбирает ID при регистрации. Регистрация устройств открытая: владение ключом не означает одобрение администратором, проверку личности или аппаратную аттестацию.

## Обмен

Все удалённые запросы идут через HTTPS/WSS. Приложение закрепляет открытый ключ из полученного вне подключения QR-кода/текста и проверяет действующий самоподписанный сертификат, сроки и имя узла/IP без публичного CA. См. [PAIRING.ru.md](PAIRING.ru.md). Перенаправления аутентификации не выполняются. Низкоуровневый транспорт допускает HTTP только для буквального loopback/localhost и адреса хоста эмулятора Android `10.0.2.2` в тестах; интерфейс добавления сервера требует HTTPS. Сервер по умолчанию отклоняет HTTP, кроме общедоступного `/health`, даже при недоверенном `X-Forwarded-Proto: https`.

1. `POST /auth/challenge`, JSON `{"public_key":"<standard base64 DER/SPKI>"}`. Принимаются только канонические ключи P-256. Ответ содержит `user_id`, `audience` (настроенный публичный URL сервера), `challenge` (32 случайных байта в base64url без дополнения) и `expires_in` (60 секунд). На этом шаге идентичность ещё не регистрируется.
2. Клиент проверяет совпадение `audience` с настроенным базовым URL. Затем подписывает точные байты UTF-8 через `SHA256withECDSA`, с тремя разделителями новой строки и без завершающего перевода строки:

   ```text
   Carriex device authentication v1
   <audience>
   <user_id>
   <challenge>
   ```

3. `POST /auth/verify`, JSON `{"challenge":"...","signature":"<standard base64 DER ECDSA signature>"}`. Каждый запрос подтверждения атомарно расходуется один раз, включая неверное доказательство. Сервер проверяет подпись, регистрирует ID устройства и возвращает `user_id`, `token`, `expires_in` (3600 секунд). Токен — 32 криптографически случайных байта в base64url без дополнения.
4. Передавайте `Authorization: Bearer <token>` в `/send`, `/messages/<user_id>` и при открытии WebSocket `/ws/<user_id>`. Токены не помещаются в URL. Сервер хранит только их хеши. Полные токены сеансов существуют только в RAM. Отдельные [учётные данные уведомлений](NOTIFICATIONS.ru.md) сохраняются на Android зашифрованными, а на сервере — хешированными; они разрешают только GET собственного количества сообщений.

Адрес сервера включён в подписанное доказательство, чтобы вредоносный сервер Carriex не смог переслать запрос подтверждения и выдать себя за устройство на другом сервере. Для рабочего развёртывания требуется `CARRIEX_AUTH_ORIGIN`; HTTP Host для этого не используется. Запуск с QR-подключением автоматически задаёт опубликованный URL. При локальной HTTP-разработке адрес может выводиться из локального URL.

Сеанс привязан к одному ID. Поле HTTP `sender`, пути входящих и WebSocket должны ему соответствовать. В WebSocket-кадре отправки `sender` можно не указывать; если он есть, требуется совпадение. В маршрутизацию поступает проверенный отправитель. Истёкшие сеансы не отправляют и не получают данные; неактивный WebSocket закрывается кодом 1008. Клиенты повторяют обмен подтверждениями при HTTP/upgrade 401, истечении аутентификации WebSocket и перезапуске сервера. Ошибка старого сокета не аннулирует новый сеанс, созданный другим запросом.

## Хранение и эксплуатационные ограничения

`src/auth.py` хранит в памяти только истекающие challenge и хешированные полные сеансы; прежний бессрочный кеш открытых ключей удалён. Таблицы ограничены глобально; по умолчанию разрешены три challenge на устройство/источник и четыре сеанса на устройство. Вытеснение старых сеансов и истечение освобождают место. Регистрация/одобрение, блокировки и версии отзыва сохраняются в SQLite. Открытая регистрация ограничена по частоте; `CARRIEX_REGISTRATION_MODE=approved` требует локального одобрения.

Используйте один процесс. Перезапуск удаляет полные токены и challenge; устройство снова доказывает владение тем же ключом. Очереди, открытые предварительные ключи, допуски/запреты и данные уведомлений сохраняются. `DELETE /auth/session` отзывает текущий полный токен; `DELETE /auth/sessions` — все полные сеансы и данные уведомлений устройства. Сокеты проверяют отзыв. Локальные команды позволяют одобрить/заблокировать ID и отозвать сеансы без публичного интерфейса администратора. Настройки и восстановление: [HARDENING.ru.md](HARDENING.ru.md). При краже закрытого ключа нужно заблокировать ID и уведомить контактов.

TLS защищает bearer-токены и поток WebSocket. Сквозное шифрование сообщений — отдельный протокол. Успешная отправка в сокет не является подтверждением доставки. См. [X3DH.ru.md](X3DH.ru.md). Реализация не проходила независимый аудит безопасности.

## Запуск

Для телефонов используйте `start-server.bat` или `python -m src.pairing` и инструкции [PAIRING.ru.md](PAIRING.ru.md). Запуск создаёт и сохраняет идентичность сервера, обслуживает HTTPS/WSS напрямую и отключает обход через HTTP и доверие заголовкам прокси.

Только для локальной разработки:

```powershell
$env:CARRIEX_ALLOW_INSECURE_HTTP='1'
.\.venv\Scripts\python.exe -m flask --app src.app:app run --host 127.0.0.1 --port 5000
```

Этот HTTP-адрес предназначен для тестовых клиентов протокола. Для приложения на эмуляторе создайте сервер с `--address https://10.0.2.2:8443`.

Для альтернативных клиентов API с публичным CA на обратном прокси задавайте `CARRIEX_TRUST_PROXY=1` только за доверенным прокси, перезаписывающим `X-Forwarded-Proto`. Backend должен слушать loopback или изолированную частную сеть; сохраняйте `Authorization` и передавайте WebSocket upgrade. Не публикуйте backend напрямую. Старый `compose.proxy.yaml` по умолчанию привязан к loopback, но `.env` HOST имеет приоритет. Обычный `compose.yaml` запускает сервер с прямым HTTPS.

Задайте `CARRIEX_AUTH_ORIGIN=https://chat.example.com` как точный публичный базовый URL клиентов, с нестандартным портом при необходимости и без завершающего `/`. Имена узлов — в нижнем регистре; стандартный HTTPS-порт 443 опускается. Другой адрес вызывает видимую ошибку аутентификации, а не создание подписи.

## Проверка

`python -m pytest -q` запускает реальные localhost-тесты аутентификации, подмены, повторов (включая одновременные), сроков сеансов/подтверждений, перезапуска, владения входящими, привязки WebSocket и сообщений. Используются настоящие сгенерированные тестовые ключи; обхода аутентификации нет.

Из Android-проекта выполните межъязыковые тесты и проверки Keystore:

```powershell
$env:CARRIEX_TEST_PYTHON=(Resolve-Path ../Carriex-server/.venv/Scripts/python.exe).Path
$env:CARRIEX_TEST_SERVER_ROOT=(Resolve-Path ../Carriex-server).Path
./gradlew.bat :app:testDebugUnitTest :app:connectedDebugAndroidTest :app:assembleDebug
```

JVM-набор проверяет подписанный обмен, кеширование и конкурентность, подмену идентичности, отклонение перенаправлений, переподключение и реальный обмен Kotlin–Flask с обновлением сеансов и восстановлением после перезапуска. Без двух переменных окружения межъязыковые тесты явно пропускаются. Инструментальный тест дважды загружает Keystore, проверяет отсутствие доступных байтов закрытого ключа и действительную подпись. Эмулятор не подтверждает физическую защиту StrongBox/TEE.

Первоисточники реализации: [Android Keystore](https://developer.android.com/privacy-and-security/keystore) и [cryptography ECDSA](https://cryptography.io/en/stable/hazmat/primitives/asymmetric/ec/).
